# Orynt

## What this is
Frontend of a web application to monitor, analyze and manage PostgreSQL databases ("Toda lentidão tem uma
origem."). Phase 1 (the login screen, the password recovery screen, the connection modal with saved connections, the application shell and a first
dashboard) plus the three report screens, Relatórios › Resumo, Relatórios › Exportação and Relatórios › Comparação, all on simulated data. The backend (OryntAPI) does not exist yet. Product decisions live in
`REQUISITOS.md` and are requirements: do not change them without the user's approval.

## Type
web/frontend - release: branch + PR to `main` on `ByGustavoo/OryntWeb` (GitHub); the branch and the PR title take the commit id, such as `ORY-2`. No CI or release workflow yet.

## Stack
React 18, TypeScript 5 (`strict`, `noUncheckedIndexedAccess`), Vite 5, React Router 6 (v7 future
flags on), CSS Modules with custom properties, Recharts, lucide-react, Geist / Geist Mono via
`@fontsource-variable`, Vitest. Same stack and folder conventions as `D:\Projetos\OrbitWeb`, from which
the design system (`src/componentes/ui/`), the HTTP layer and the layout were adapted.

## Conventions
* All identifiers, types, fields, files and folders in Portuguese (`ConexaoDTO`, `tempoMedioMs`, `aoConectar`); enum values in UPPER_CASE (`'ULTIMAS_24_HORAS'`). Interface text is accented pt-BR in sentence case.
* No comments in source, CSS, config or HTML. The only exceptions are `.env.example` and `/// <reference>`.
* No hex colors in components: colors come from `temas.css` tokens (`[data-tema='escuro']`, `[data-tema='claro']`). The only hex outside it is the theme preview miniature in `SecaoAparencia.module.css`.
* Pages and components never call `fetch` or `clienteHttp`; they call services. API paths live only in `src/api/rotasApi.ts`.
* `import.meta.env` and `window.__ORYNT_CONFIG__` are read only in `src/configuracoes/ambiente.ts`.
* Routes only from `src/rotas/caminhos.ts`. Imports between folders use the `@/` alias.
* New interface work goes through the `elite-web-experience` skill and is verified in Chrome.

## Security rules (from REQUISITOS.md)
* The database password is never written to `localStorage`, `sessionStorage`, a cookie, the URL or the console. `useFluxoConexao` drops it from state as soon as the connection is accepted.
* The app stores only `orynt:tema` and `orynt:menu-recolhido`. Saved connections belong to the account and come from the API. The simulator, playing the server, keeps them in `orynt:simulacao:conexoes-salvas` (id, type, name, host, port, database, user and last use; `lerConexoesSalvas` strips any other field, so a password can never be written there).
* The real session is an `HttpOnly` cookie set by the API at login; the app never reads it. `acessoSimulado.ts` and `sessaoSimulada.ts` are the simulator playing the server and go away with it.
* The password recovery never tells whether an e-mail has an account (`REQUISITOS.md`, "Recuperação de senha"): the code step opens for any well-formed e-mail and a wrong code, an expired code and an e-mail without an account get one message. Do not add a branch in the front that depends on the account existing. E-mail, code, reset token and new password live only in React state: never in the URL, the history state, storage, a cookie or the console.
* The login is fictitious (`REQUISITOS.md`, "Acesso"): the simulator compares the form with `credenciaisDemonstracao.ts` (`demo@orynt.local` / `orynt-demo`). The login password follows the same rule as the database password: never stored, dropped from state when accepted. Never present this login as production-grade.

## Gotchas
* Without a `.env`, the app runs on simulated data (`VITE_FONTE_DADOS=simulada`). With `VITE_FONTE_DADOS=api`, the simulator is not bundled (checked by building both ways).
* Nothing simulated may look real: `ConexaoDTO.simulada` drives the "Demonstração" badge in the account menu (shown only while a connection is active) and the notices in the connection modal, the success notification, the dashboard and the settings. Keep them when adding screens.
* There is no `/conexao` page. The login goes straight to `/dashboard`, and `ProvedorConexao` decides what the shell shows through `situacao`: `VERIFICANDO` (only this one blocks the shell, in `RotaProtegida`), `CONECTANDO` (reactivating the most recently used saved connection), `CONECTADA`, `DESCONECTADA` (with `falhaReconexao` when the reactivation failed) and `INDISPONIVEL` (the check itself failed; `verificarNovamente` retries). The shell renders in every state but the first, so nothing inside it may assume a connection: read `conexao` from `useConexao()` and handle `null`.
* The connection check runs while the login check is still running (`temSessao` is true until the user turns out to be anonymous) and runs again after a login. A `401` on `GET /conexoes` means no session and sends to `/login`; a `401` on `GET /conexoes/atual` only means no active connection.
* The connection modal never opens by itself: only a click opens it (`abrir` in `ProvedorNovaConexao`), from "Conectar ao banco" on the empty dashboard, "Nova conexão" in the header and the saved connections. `ModalConexao` is lazy and keeps the typed fields between openings, except the password; after a successful connection the next opening remounts it (`geracao`) so the form starts empty.
* Switching connections keeps the current one on screen until the new one answers (`alvo` is the one being activated). `DashboardConectado` is keyed by the connection id, so the data reloads on a switch.
* The modal actions live in the `Modal` footer and submit the form through the `form` attribute; do not move them back inside `FormularioConexao`.
* `Modal` records the element to give focus back to only when the focus is outside its panel, so a modal mounted already open (rename, the lazy connection modal) survives the double effect of StrictMode.
* The connection scenario panel (`PainelSimulacao`, inside the modal) and `window.oryntSimulacao` exist only in development. Console controls: `cenario('SENHA_INCORRETA' | 'SERVIDOR_INACESSIVEL' | 'BANCO_INEXISTENTE' | 'TEMPO_ESGOTADO' | 'SUCESSO')` (also applies to activating a saved connection), `falhar('/dashboard')` (`false` turns it off; `falhar('/conexoes')` shows the failed-check state, `falhar('/relatorios')` the error state of the three report screens), `latencia(8000)`, `esvaziar()` (empty states of the dashboard and of the report screens; `esvaziar(false)` restores), `encerrarSessao()` (drops the active connection), `expirarCodigo()` and `expirarRedefinicao()` (end the validity of the recovery code and of the reset token right away; `falhar('/autenticacao/recuperacao')` shows the server error of the three recovery steps), `sair()` (drops login and connection, then reloads on `/login`; the account menu in the header also has a "Sair" button).
* Editing a provider file that also exports its hook makes Vite recreate the context on hot reload, and a lazily loaded page then fails with "precisa estar dentro de"; reload the page before reading that as a bug.
* The dashboard data is deterministic: `series.ts` seeds every interval with its own start time, and the indicators are derived from the same series and query list. `series.test.ts` enforces that the total equals the sum of the chart and that the slow-query count matches the table.
* `VariacaoIndicador` colors the arrow and the percentage only when it gets `favoravel` (`'ALTA'` or `'QUEDA'`, the direction that counts as good). On the dashboard both cards have it: "Consultas executadas" is green when it rises and red when it falls (the user asked on 12 October 2026), "Tempo médio de execução" the opposite. In Relatórios the volume stays neutral, as `REQUISITOS.md` says, so `IndicadoresRelatorio` passes it only for the average time. The `%` is a separate span in the interface font: the Geist Mono glyph was hard to read at 12px.
* The indicator card (`IndicadorNumerico`, shared by the dashboard, Resumo and Comparação) draws its icon at 18px inside a 32px tile (the user asked on 12 October 2026 for icons that are visible and centered): both sizes are even on purpose, because the old 15px icon in a 26px tile left 5.5px on each side and could not sit on the pixel grid. On mount the cards cascade from left to right (`--ordem` comes from `:nth-child`, up to four cards, and `--entrada` is the resulting delay, which `MedidorOcupacao` also reads to grow its bar) and each icon draws its own strokes: a layout effect sets `pathLength="1"` on the children of the lucide SVG so one `stroke-dashoffset` keyframe fits any icon. The animations sit on the label, the value and the context, not on the card itself, because the grid shows `--borda` through its 1px gaps and a fading card would flash that color. The label row reserves two lines (`min-height: 2.25rem`), so a label that wraps does not push its value below the neighbours; between 901px and 1000px of `resumo` width the card tightens its side padding and the label gap, which is what keeps "Tempo médio de execução" on one line at 1280px with the menu open. The hover only lights the card and rings the tile: the cards are not clickable, so do not add a lift or a pointer. Connections use `Plug`, the counterpart of the `Unplug` shown when there is no connection.
* The dashboard blocks enter one after the other (the user asked on 12 October 2026 to animate every card of the screen): `.blocos > *` in `PaginaDashboard.module.css` takes `--bloco` from `:nth-child` and starts one page step after the previous block, on top of the page entrance of `LayoutAplicacao`. The activity chart draws over 900ms with `ease-out` (`DURACAO_TRACADO_MS`), the same time `useContagem` takes, so the line and the numbers settle together; the report charts keep 480ms. In `TabelaConsultas` (shared with Resumo) the rows cascade with `item-em-cascata` and the share bars grow from zero, but only while `entrando` is true: the bar of the last row turns it off on `animationend`. Do not make those classes permanent, because React moves the `tr` nodes when the table is sorted and a moved node restarts its CSS animation, which replayed the entrance on some rows only.
* The SQL cell of `TabelaConsultas` is `ConsultaSql` (`src/componentes/comum/`, asked by the user on 12 October 2026): `TrechoSql` plus a button that shows the whole query and one that copies it. `TrechoSql` alone stays in `DestaquesRelatorio` and in `ConsultasComparadas`, where the 38% column is too narrow to give up the width of two buttons without truncating almost every query. The toggle exists only while the text is cut, which `ConsultaSql` measures on the `code` element (`scrollHeight` against `clientHeight`, again on resize and when the fonts load); the height animation runs on the wrapper (`moldura`), not on the `code`, so that measurement is never taken in the middle of it. Clicking the cut text only opens it: closing is the button's job, so a double click still selects a word. The copied text is the raw SQL, with no demo notice, on purpose (`REQUISITOS.md`). The copy button is hidden until the row is hovered or focused by the keyboard on devices with hover and always visible on touch; the rule is `:has(:focus-visible)`, not `:focus-within`, because a mouse click leaves the focus on the button and it stayed on screen after the confirmation (the user reported it on 12 October 2026); the confirmation is the check icon plus a `role="status"`, as in `DestaquesRelatorio`, not a notification. The copy icon must never come back on screen after the check (the user reported it twice on 12 October 2026): `faseCopia` goes from `CONFIRMANDO` (2.4s, button forced visible) to `LIBERADA`, in which the check stays and the button follows the hover again, and only the `transitionend` of its opacity reaching 0 puts the copy icon back (`PARADA`). Swapping the icon on the timer made it flash during the 120ms fade. Where the button is always visible (no hover) there is no fade to wait for, so the timer swaps it directly. In the card layout the table moves the two buttons to the foot of the card through `classeAcoes` (absolute against the `tr`), because beside the text they took a third of a 320px card. Checking the copy through the Chrome extension must not touch the clipboard of the machine: replace `navigator.clipboard.writeText` in the page first and read the text from there.
* The first theme is dark: `public/tema-inicial.js` applies it before React mounts (no inline script). If `CHAVE_TEMA` changes, update that file too.
* A `Botao` with `carregando` is `aria-disabled`, not `disabled`, so it keeps focus while the request runs. Do not switch it back.
* The palette is neutral black or white plus blue (decided with the login screen). Three blue roles, do not merge them: `--destaque` is for text, icons, borders and focus on a surface; `--acao`, `--acao-forte` and `--acao-contraste` are for filled buttons (white text needs the deeper blue); `--grafico-1` is for chart marks and was validated against both surfaces with the dataviz palette validator.
* The notification card has its own tokens in `temas.css` (`--notificacao-fundo`, `--notificacao-borda`, `--notificacao-realce` for the hover of the close button). `Notificacao.tsx`, its CSS and `ProvedorNotificacoes` are otherwise the same files as in OrbitWeb (plus one print rule that hides the notification area); the user asked on 11 October 2026 for the card to stand out like there, and on the black palette `--superficie-elevada` with `--borda` gave about half of OrbitWeb's edge contrast. The dark values (`#1b1b1b` on `#272727`) reproduce OrbitWeb's ratios (card against page 1.15, border against card 1.16); the light ones equal `--superficie-elevada`, `--borda` and `--superficie-suave`. Other floating surfaces keep `--superficie-elevada`.
* The brand mark (`MarcaOrynt`) is flat, on purpose (the user asked for no 3D on 11 October 2026): a donut chart that forms the "O" of the name, with one slice pulled out of the ring. The ring takes `--marca-corpo` (the text color) and the slice `--marca-destaque` (the accent blue), both aliases in `temas.css`, so it follows the theme. The slice slides out on the login entrance (`animada`) and snaps back into the ring when a link around the mark is hovered. The two shapes are filled paths on a 32-unit grid, not strokes (redrawn on 11 October 2026, when the user said the mark looked pixelated on a 100% scale monitor): the ring is 270° of a donut centred on (15, 17) with radii 15 and 8, the slice is the missing quarter moved 2 units up and right. Every straight edge and every extreme of the circles falls on a whole unit, so at 32px, the size used in the shell, the login and the 404 page, the cuts are sharp and only the curves are antialiased: keep whole numbers in the paths and render the mark at 32px or a multiple of it wherever it matters (the splash uses 44). Below 32px `MarcaOrynt` switches to a second drawing on a 24-unit grid (`DESENHO_COMPACTO`: centre (11, 13), radii 11 and 6, same 2-unit offset), because the 32-unit paths scaled to 24px put every cut on a fraction of a pixel; the header in drawer mode uses it at 24px (the user said on 12 October 2026 that the 32px mark looked too big beside the header icons on smaller screens), inside a link the size of `--alvo-toque`. `--fatia-encaixada` is that same 2-unit offset: change the two together. `public/icone.svg` is a static copy of the same two paths on the same 32-unit grid, with no tile behind it (the user asked on 11 October 2026 for the tab icon to equal the mark in the shell). It cannot read the theme tokens, so it repeats the values of `--texto` and `--destaque` and picks them with `prefers-color-scheme` (ring `#fafafa` and slice `#5b9cff` on dark browser chrome, `#0f1115` and `#1d5bd8` on light): it follows the browser's scheme, not the app theme, so the ring always contrasts with the tab. Change the paths and those four colors together with the mark and `temas.css`.
* The login brand panel (`PainelMonitoramento`) uses the `--identidade-*` tokens, which follow the theme.
* The login illustration is a pure function of a step counter (`montarCena(passo)` in `roteiroCena.ts`, covered by tests); `useCenaMonitoramento` only advances the step once a second, and stops when the panel is off screen, the tab is hidden or the system asks for reduced motion. The chart slides with the Web Animations API, so the scene must not be remounted per step.
* The login chart line is a monotone curve (`tracarCurvaSuave` in `src/utilitarios/tracado.ts`, covered by tests), so smoothing never overshoots the peak. The scene's phase accents (red ring on the chart card during `PICO`, blue ring on the origin card during `ORIGEM`) are driven by `data-fase` in `CenaMonitoramento.module.css`, not by component state.
* The line from the chart card to the origin card (`RotaCena`) is an SVG path measured from its own box and drawn with `stroke-dashoffset`, so it travels through the corner to the node. It replays by remounting on `EstadoCena.rastreio`, which changes only on the step where the phase becomes `RASTREANDO` (tested); do not swap the animation by phase selector, or it restarts when the phase leaves.
* The login panel is clipped to the viewport height on desktop: the tiers in `PainelMonitoramento.module.css` and `CenaMonitoramento.module.css` (`max-height` 899, 860, 799, 679, 579) drop pieces so nothing overflows; the indicator card is the first to go, below 900px of height. Re-check 1280x720 and 1024x768 after changing its content.
* `/login` never shows the splash: `RotaVisitante` renders the page while the session check is still running and only redirects once the user turns out to be signed in, and the page's `Suspense` fallback is empty. Elsewhere `TelaVerificacao` stays blank for the first 600ms, so a quick check shows no logo screen at all.
* The login entrance is one top-to-bottom cascade across both halves: `--entrada-inicio`, `--entrada-passo` and `--entrada-duracao` on `.pagina` set the pace, each piece takes a step number by its height on the screen (the left column in `LayoutAcesso.module.css`, `CabecalhoAcesso.module.css` and `FormularioAcesso.module.css`, the right in `PainelMonitoramento.module.css` and the `--entrada-*` offsets on `.cena`), and everything falls into place from above (`--animacao-emergir`). The `Suspense` fallback of the demo access card reserves its height (`reservaDemonstracao`), so the centered column does not jump when the lazy chunk arrives; adjust it if that card changes size.
* The login column (brand, title, form) is centered in the left half, both ways, independently of the panel on the right; the brand and the title are centered text, the fields stay left-aligned.
* `/login` and `/recuperar-senha` are children of one layout route (`LayoutAcesso`), so the brand, the theme button and the animated panel stay mounted when the user goes from one to the other and only the left column changes. The two pages return fragments whose pieces are direct children of the layout's `.coluna`. The layout also carries, in plain React state handed down as the outlet context (`useContextoAcesso`), the e-mail typed on one screen for the other and the "password changed" flag that makes the login show its notice: on purpose not the history state, so nothing about the recovery survives a reload. The hook lives in `contextoAcesso.ts`, apart from the layout component, so hot reload does not recreate it.
* The entrance cascade of that layout has two paces: `.area` starts with the long one from `.pagina` and `LayoutAcesso` switches `data-ritmo` to `troca` 1400ms after mounting (420ms, 40ms steps, no initial delay). Every later mount in the left column (the other page, the next recovery step, whose header and form are keyed by the step) replays `--animacao-emergir` at the short pace. Keep `DURACAO_DA_ENTRADA_MS` longer than the first cascade, or it is cut in the middle.
* The recovery flow (`useFluxoRecuperacaoSenha`) is `EMAIL`, `CODIGO`, `SENHA`. The reset token returned by the code check stays in a ref. A wrong code clears the field and shows the message on the field; attempts exhausted (`429`, `LIMITE_EXCEDIDO`, problem type `recovery-attempts-exceeded`) and server failures show a note above it and keep the typed code when the failure was not about the code. An expired reset token (`invalid-reset-token`) sends the user back to `EMAIL` with the explanation. The focus moves to the first field of each step from an effect in the page, and a visually hidden `role="status"` announces the step.
* `CampoCodigo` (`src/componentes/ui/`) is one real `input` with `opacity: 0` laid over six drawn cells, not six inputs: that is what keeps paste, `autocomplete="one-time-code"` and screen readers working. It has no `maxLength` (a pasted "482 913" would be cut before the digits are filtered), keeps the caret at the end and replaces the whole value on paste. The automatic submission on the sixth digit is in `alterarCodigo`, which ignores a change that leaves the value as it was: without that guard, typing a seventh digit after a network failure would submit again.
* The simulator keeps the recovery state in memory (`recuperacaoSimulada.ts`), so a reload drops codes and tokens, and it counts attempts for e-mails without an account too, so the `429` reveals nothing. The 60s between two codes for the same e-mail is enforced there as well as on screen: inside it a new request answers `202` and keeps the current code. The "Caixa de entrada simulada" card (`DemonstracaoRecuperacao`, lazy and bundled only with simulated data, like `AcessoDemonstracao`, whose CSS it reuses) is the only place that says an e-mail got no message; that is the simulator showing the inbox, not the screen revealing the account.
* The strength meter (`MedidorForcaSenha`) is advice only: the rule that accepts a password is `validarNovaSenha` (8 to 128 characters). `forcaSenha.ts` discounts common words, pieces of the e-mail, sequences and repetitions from the length before scoring. The field shows one message at a time (the user asked on 12 October 2026 to stop showing the length error and the meter text together): the level and its advice go in as the `dica` of `CampoSenha`, so the field error replaces them, and the bars sit between the control and that message through `complemento`, a slot of `EstruturaCampo` that `CampoSenha` passes on. The length error counts down ("Use pelo menos 8 caracteres. Faltam 3."), which keeps what the meter text was saying. Keep the advice sentences short enough for one line at the 376px column, or the fields below jump while the user types.
* `LayoutAcesso` has a tier for short desktop viewports (`min-width: 960px` and `max-height: 760px`: 16px of vertical padding and a 20px column gap, and the recovery forms drop their gap to 16px under the same height), which is what makes the three recovery steps fit in 1280x720 with the demo card, even with both field errors showing (the user asked on 12 October 2026). The login takes the same tier, so the brand does not change rhythm between the two screens. Measure step 3 at 1280x720 again after adding anything to it. Checking the paste through the Chrome extension must not touch the clipboard of the machine: dispatch a `ClipboardEvent('paste')` with a `DataTransfer` on `#recuperacao-codigo`.
* A `Botao` that moves its arrow on hover must select it as a direct child (`.enviar > svg:last-child`, `.entrar > svg:last-child`).
