# Orynt

## What this is
Frontend of a web application to monitor, analyze and manage PostgreSQL databases ("Toda lentidão tem uma
origem."). Phase 1 (the login screen, the password recovery screen, the connection modal with saved connections, the application shell and a first
dashboard) plus the three report screens, Relatórios › Resumo, Relatórios › Exportação and Relatórios › Comparação, three screens of Consultas SQL, Todas, Histórico and Planos de execução, Objetos do banco › Visões, Índices, Tabelas and Funções, and Usuários e permissões › Papéis, Sessões and Permissões, all on simulated data. The backend (OryntAPI) does not exist yet. Product decisions live in
`REQUISITOS.md` and are requirements: do not change them without the user's approval.

## Type
web/frontend - release: branch + PR to `main` on `ByGustavoo/OryntWeb` (GitHub); the branch and the PR title take the commit id, such as `ORY-2`. No CI or release workflow yet.

## Stack
React 18, TypeScript 5 (`strict`, `noUncheckedIndexedAccess`), Vite 5, React Router 6 (v7 future
flags on), CSS Modules with custom properties, Recharts, lucide-react, Geist / Geist Mono via
`@fontsource-variable`, Vitest. Same stack and folder conventions as `D:\Projetos\OrbitWeb`, from which
the design system (`src/componentes/ui/`), the HTTP layer and the layout were adapted.

## Conventions
* All identifiers, types, fields, files and folders in Portuguese (`ConexaoDTO`, `tempoMedioMs`, `aoConectar`); enum values in UPPER_CASE (`'ULTIMAS_24_HORAS'`). Interface text is accented pt-BR in sentence case.
* No comments in source, CSS, config or HTML. The only exceptions are `.env.example` and `/// <reference>`.
* No hex colors in components: colors come from `temas.css` tokens (`[data-tema='escuro']`, `[data-tema='claro']`). The only hex outside it is the theme preview miniature in `SecaoAparencia.module.css`.
* Pages and components never call `fetch` or `clienteHttp`; they call services. API paths live only in `src/api/rotasApi.ts`.
* `import.meta.env` and `window.__ORYNT_CONFIG__` are read only in `src/configuracoes/ambiente.ts`.
* Routes only from `src/rotas/caminhos.ts`. Imports between folders use the `@/` alias.
* New interface work goes through the `elite-web-experience` skill and is verified in Chrome.

## Security rules (from REQUISITOS.md)
* The database password is never written to `localStorage`, `sessionStorage`, a cookie, the URL or the console. `useFluxoConexao` drops it from state as soon as the connection is accepted.
* The app stores only `orynt:tema` and `orynt:menu-recolhido`. Saved connections belong to the account and come from the API. The simulator, playing the server, keeps them in `orynt:simulacao:conexoes-salvas` (id, type, name, host, port, database, user and last use; `lerConexoesSalvas` strips any other field, so a password can never be written there).
* The real session is an `HttpOnly` cookie set by the API at login; the app never reads it. `acessoSimulado.ts` and `sessaoSimulada.ts` are the simulator playing the server and go away with it.
* The password recovery never tells whether an e-mail has an account (`REQUISITOS.md`, "Recuperação de senha"): the code step opens for any well-formed e-mail and a wrong code, an expired code and an e-mail without an account get one message. Do not add a branch in the front that depends on the account existing. E-mail, code, reset token and new password live only in React state: never in the URL, the history state, storage, a cookie or the console.
* The login is fictitious (`REQUISITOS.md`, "Acesso"): the simulator compares the form with `credenciaisDemonstracao.ts` (`demo@orynt.local` / `orynt-demo`). The login password follows the same rule as the database password: never stored, dropped from state when accepted. Never present this login as production-grade.

## Gotchas
* Without a `.env`, the app runs on simulated data (`VITE_FONTE_DADOS=simulada`). With `VITE_FONTE_DADOS=api`, the simulator is not bundled (checked by building both ways).
* Nothing simulated may look real: `ConexaoDTO.simulada` drives the "Demonstração" badge in the account menu (shown only while a connection is active) and the notices in the connection modal, the success notification, the dashboard and the settings. Keep them when adding screens.
* There is no `/conexao` page. The login goes straight to `/dashboard`, and `ProvedorConexao` decides what the shell shows through `situacao`: `VERIFICANDO` (only this one blocks the shell, in `RotaProtegida`), `CONECTANDO` (reactivating the most recently used saved connection), `CONECTADA`, `DESCONECTADA` (with `falhaReconexao` when the reactivation failed) and `INDISPONIVEL` (the check itself failed; `verificarNovamente` retries). The shell renders in every state but the first, so nothing inside it may assume a connection: read `conexao` from `useConexao()` and handle `null`.
* The connection check runs while the login check is still running (`temSessao` is true until the user turns out to be anonymous) and runs again after a login. A `401` on `GET /conexoes` means no session and sends to `/login`; a `401` on `GET /conexoes/atual` only means no active connection.
* The connection modal never opens by itself: only a click opens it (`abrir` in `ProvedorNovaConexao`), from "Conectar ao banco" on the empty dashboard, "Nova conexão" in the header and the saved connections. `ModalConexao` is lazy and keeps the typed fields between openings, except the password; after a successful connection the next opening remounts it (`geracao`) so the form starts empty.
* Switching connections keeps the current one on screen until the new one answers (`alvo` is the one being activated). `DashboardConectado` is keyed by the connection id, so the data reloads on a switch.
* The modal actions live in the `Modal` footer and submit the form through the `form` attribute; do not move them back inside `FormularioConexao`.
* `Modal` records the element to give focus back to only when the focus is outside its panel, so a modal mounted already open (rename, the lazy connection modal) survives the double effect of StrictMode.
* Consultas SQL › Todas (`PaginaTodasConsultas`, `REQUISITOS.md`, "Consultas SQL: Todas") is the only list the API searches, filters, orders and pages (`GET /consultas`): the front never holds the whole list, so do not sort or filter `itens` in the browser. The page keeps, beside each answer, the filters that produced it (`ListaCarregada.aplicados`), and the count, the marked terms, the empty-state sentence and the period of the detail modal read those, not the filters being requested: while a new search loads, the previous rows stay on screen dimmed, and with the requested filters the screen said "42 de 42 consultas" over rows that did not match (seen on 12 October 2026). Only the controls (search field, segmented control, sort arrows) follow the requested filters. A change of period is the exception (the user asked on 12 October 2026, because the dimmed rows of the old period read as a freeze): `trocandoDePeriodo` compares the period of `aplicados` with the requested one, with no `lista.carregando` in it, so not even the first render after the click shows the old rows, and the rows, the count and the pagination give way to `EsqueletoTodasConsultas` (same file and same `MolduraDaTabela` as the table, so the header and the sort buttons stay; `imediato`, without the 300ms wait) with as many rows as the page had. Its bars repeat the widest content of each column (89px for the "Moderada" badge, a 16px spacer for the arrow) and every other row has two lines, which keeps the seven column widths identical to the loaded table and the height within 8px at 1920px: measure both again after changing a column. The first load uses the same skeleton with 8 rows and the usual wait. Set `latencia(5000)` only after the first rows are on screen, or the reload itself takes that long, and turn it off at the end, because it is stored. The filters live in the history state as `{ lista }` (`useFiltrosConsultas`, read through `lerFiltros`, which replaces each invalid field by its default and so accepts the partial state the Dashboard sends); any change but the page goes back to page 1 (`aplicarMudanca`). A page past the end comes back empty with the totals and the page moves to the last one.
* The simulator lists 42 queries because the indicators always said 42 distinct ones: the ten of `consultasFicticias` and 32 secondary ones, all fast, whose shares and times are normalised so that they keep the old "other queries" total (29.29% of the executions at 4.5 ms on average) and the dashboard and report numbers did not move. `gerarConsultasDetalhadas` reuses `gerarConsultas` for the ten, so the dashboard table is literally the top of the list; `consultas.test.ts` enforces that, that the executions add up to `totalConsultas`, that the slow ones match the indicator and that the count equals `consultasDistintas`. A secondary query must stay under 100 ms after the 1.08 period factor and under the weight of the lightest of the ten (share times time below about 0.27), or it becomes "Moderada" or enters the dashboard top ten: check both before adding one.
* The row of `TabelaTodasConsultas` opens the detail modal, so it does not use `ConsultaSql` (whose click expands the text in place): the SQL is a `TrechoSql` inside a `button`, the `tr` takes the click and moves the focus to that button first, which is what lets `Modal` give the focus back to the row when the modal closes. `DetalheConsulta` is a centered `Modal` with `tamanho="lg"` (the user asked on 12 October 2026 to replace the drawer on the right it first was, so `Modal` no longer has a `posicao` prop), and below 600px the bottom sheet every modal already is. Its SQL box reserves two lines (`min-height: 3em` on the `code`), which keeps the modal at one height, 645px at 760px of width for the 42 simulated queries, so the arrows of the footer stay under the pointer while stepping through the list and the whole modal fits 1280x720 without scrolling; measure both again after adding a block to it. "No período" goes from two columns to four from 600px of `detalhe-consulta`, where the longest value of the 30 days ("46 h 42 min") still fits. The marked terms come from `TrechoSql`'s `termos` prop: `destacarSql` takes the stretches from `intervalosMarcados`, which normalises the SQL one UTF-16 unit at a time so the positions still point into the original text. The mark color is `--busca-realce` in `temas.css`.
* Consultas SQL › Histórico (`PaginaHistoricoConsulta`, `REQUISITOS.md`, "Consultas SQL: Histórico") shows one query at a time and is one request, `GET /consultas/{id}/historico`, and one DTO, so its blocks cannot disagree: the query with the numbers of the period (the same `ConsultaDetalhadaDTO` the list returns), the two variations, the position by weight with the neighbour ids and the intervals. The intervals are the ones of the dashboard activity chart (`intervalosPorPeriodo` and `minutosPorIntervalo` in `regras/historicoConsulta.ts` repeat the table of the contract, and `historicoConsulta.test.ts` checks them against `janelasPeriodo`). The selection lives in the history state as `{ historico: { consulta, periodo } }` (`useSelecaoHistorico`, read through `lerSelecao`; `lerIdDaConsulta` only accepts letters, digits, `_`, `.`, `:` and `-`, because the id goes into the path of the route). `consulta` is `null` when the screen is opened from the menu: the page then asks `servicoConsultas.buscarMaisPesada` (the first of `GET /consultas`) and shows that one. The id is written to the state only when something changes (`mudarPeriodo` pins the loaded query, so a new period keeps the query on screen): writing it right after the first answer would change the dependency of the fetch and ask for the same history twice. The page keeps, beside each answer, the selection that produced it (`Carga.pedido`) and compares it by identity with the current one: any difference shows the skeleton at once (`trocando`), as on the other screens. A `404` is not an error state: `carregar` turns it into `NAO_ENCONTRADA`, which offers the heaviest query. A change of connection resets `consulta` to `null` from an effect in the page.
* `ConsultaEmAnalise` stays mounted outside `ConteudoAssincrono`, so the selector works while the blocks load. It shows the SQL of the loaded history when the requested query is the same (a change of period keeps the SQL and hides only the performance badge), the SQL of the suggestion that was just picked (`escolhida`) while its history loads, and skeleton lines otherwise (the arrows only know the id).
