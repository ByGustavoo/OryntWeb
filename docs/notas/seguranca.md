# Segurança

Regras de segurança completas (de `REQUISITOS.md`). O resumo fica no `CLAUDE.md`.

* The database password is never written to `localStorage`, `sessionStorage`, a cookie, the URL or the console. `useFluxoConexao` drops it from state as soon as the connection is accepted.
* The app stores only `orynt:tema` and `orynt:menu-recolhido`. Saved connections belong to the account and come from the API. The simulator, playing the server, keeps them in `orynt:simulacao:conexoes-salvas` (id, type, name, host, port, database, user and last use; `lerConexoesSalvas` strips any other field, so a password can never be written there).
* The password of a role (Papéis) follows the same rule: it lives only in the state of `FormularioPapel`, dies with the modal, and only its SCRAM-SHA-256 verifier reaches the API. The history and the simulator (`orynt:simulacao:alteracoes`) never keep the verifier (`ocultarSenhas`).
* The real session is an `HttpOnly` cookie set by the API at login; the app never reads it. `acessoSimulado.ts` and `sessaoSimulada.ts` are the simulator playing the server and go away with it.
* The password recovery never tells whether an e-mail has an account (`REQUISITOS.md`, "Recuperação de senha"): the code step opens for any well-formed e-mail and a wrong code, an expired code and an e-mail without an account get one message. Do not add a branch in the front that depends on the account existing. E-mail, code, reset token and new password live only in React state: never in the URL, the history state, storage, a cookie or the console.
* The Orynt accounts (`REQUISITOS.md`, "Administração: Usuários e Auditoria") are not PostgreSQL roles: Usuários e permissões is the database, Administração is who uses the Orynt. Every simulator route declares its `acesso` in `transporteSimulado` (`PUBLICA`, `AUTENTICADA`, a list of `CodigoPermissao` or a function of the request, as `permissoesDaAlteracao`), and `autorizar` checks it before the handler on every request, with the permissions read from storage at that moment, so a revoked permission fails on the next call and a direct call through a service gets the same `403` as the button. The `403` is the new `PROIBIDO` type of `ErroApi` (it was folded into `NAO_AUTORIZADO`, which the pages read as a lost connection). The front uses the same rules from `regras/permissoesConta.ts` (catalog, profiles, `telasDoOrynt`, `avaliarMudancaDeConta`, `motivoDoBloqueioDaPermissao`, `permissoesDasOperacoes`) to hide menu items, block buttons with the reason and show `SemAcessoNaTela`, never as the only guard. A new screen needs its entry in `telasDoOrynt`; a new route needs its `acesso` and, when protected, a `descricao`, which is the sentence of the `ACESSO_NEGADO` event.
* The Papéis and Permissões buttons check two things: the account permission (`PermissaoDasAlteracoes`, a context the page provides, read by `BotaoDeAlteracao`) and the database role (`capacidade`). The review in `ModalAlteracao` names the exact account permission missing for the operations (`permissoesDasOperacoes`). Tabelas, Views and Funções ask "Quem acessa" only with `BANCO_ACESSOS_VER`. Saved connections are per account since this change (`conexoesSalvasSimuladas` keys them by account id and moved the old flat list to the demo account); without `CONEXOES_USAR` the header hides "Nova conexão" and `PainelSemConexao` says why.
* Every handler takes a fourth argument, `contexto` (`{ conta }`, the session account), and records its own audit events through `registrarEvento`; never write a password, a code, a token or a request body into an event. `atenderNoSimulador(requisicao, agora)` runs a request without the latency, which is what `administracao.test.ts` uses for the end-to-end checks (it stubs `window` and `document` inside `vi.hoisted`, because the transport touches `window` at import). Handlers may be async now (the hashes are WebCrypto).
* Account passwords: the simulator keeps a PBKDF2-SHA-256 hash with salt, never the password; the demo account keeps the marker `SENHA_DA_DEMONSTRACAO` and always takes `orynt-demo`, because the login card offers it (recovery of the demo account still does not change it). Invites carry a random token whose SHA-256 is stored; the link goes in the fragment (`/ativar-conta#convite=`) and `PaginaAtivarConta` reads it in the `useState` initializer without side effects and clears the address in an effect: clearing it in the initializer made StrictMode read an empty hash on the second call and show "Este convite não vale mais" (seen on 20 October 2026). `/ativar-conta` sits in its own `LayoutAcesso` route outside `RotaVisitante`, so it works with another account open in the same browser. Opening it with only a new hash on a page already loaded does not reload it; check it with a real reload.
* Login lockout counts failures per e-mail, with or without an account, so the `429` reveals nothing; a reset password and "Desbloquear" clear it. A deactivated account with the right password gets `403` and "Esta conta está desativada".
* The audit is filtered and paged by the simulator (`GET /auditoria`, 25 per page, `filtrarEventos` of `regras/auditoria.ts` playing the server query). The page keeps the filters of the answer (`Carga.pedido`) for the count, the empty sentence and the summary, dims the previous rows while a new answer loads, and the detail arrows cross pages (`chegada` opens the first or last event when the next page arrives). The list starts empty: nothing is seeded, by request ("não invente atividades"). Each screen opened writes one `TELA_ACESSADA`, including every reload while checking the UI.
* The login is fictitious (`REQUISITOS.md`, "Acesso"): the simulator compares the form with `credenciaisDemonstracao.ts` (`demo@orynt.local` / `orynt-demo`). The login password follows the same rule as the database password: never stored, dropped from state when accepted. Never present this login as production-grade.
