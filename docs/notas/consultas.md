# Consultas SQL: Todas, Histórico e Planos de execução

* Consultas SQL › Todas (`PaginaTodasConsultas`, `REQUISITOS.md`, "Consultas SQL: Todas") is the only list the API searches, filters, orders and pages (`GET /consultas`): the front never holds the whole list, so do not sort or filter `itens` in the browser. The page keeps, beside each answer, the filters that produced it (`ListaCarregada.aplicados`), and the count, the marked terms, the empty-state sentence and the period of the detail modal read those, not the filters being requested: while a new search loads, the previous rows stay on screen dimmed, and with the requested filters the screen said "42 de 42 consultas" over rows that did not match (seen on 12 October 2026). Only the controls (search field, segmented control, sort arrows) follow the requested filters. A change of period is the exception (the user asked on 12 October 2026, because the dimmed rows of the old period read as a freeze): `trocandoDePeriodo` compares the period of `aplicados` with the requested one, with no `lista.carregando` in it, so not even the first render after the click shows the old rows, and the rows, the count and the pagination give way to `EsqueletoTodasConsultas` (same file and same `MolduraDaTabela` as the table, so the header and the sort buttons stay; `imediato`, without the 300ms wait) with as many rows as the page had. Its bars repeat the widest content of each column (89px for the "Moderada" badge, a 16px spacer for the arrow) and every other row has two lines, which keeps the seven column widths identical to the loaded table and the height within 8px at 1920px: measure both again after changing a column. The first load uses the same skeleton with 8 rows and the usual wait. Set `latencia(5000)` only after the first rows are on screen, or the reload itself takes that long, and turn it off at the end, because it is stored. The filters live in the history state as `{ lista }` (`useFiltrosConsultas`, read through `lerFiltros`, which replaces each invalid field by its default and so accepts the partial state the Dashboard sends); any change but the page goes back to page 1 (`aplicarMudanca`). A page past the end comes back empty with the totals and the page moves to the last one.
* The simulator lists 42 queries because the indicators always said 42 distinct ones: the ten of `consultasFicticias` and 32 secondary ones, all fast, whose shares and times are normalised so that they keep the old "other queries" total (29.29% of the executions at 4.5 ms on average) and the dashboard and report numbers did not move. `gerarConsultasDetalhadas` reuses `gerarConsultas` for the ten, so the dashboard table is literally the top of the list; `consultas.test.ts` enforces that, that the executions add up to `totalConsultas`, that the slow ones match the indicator and that the count equals `consultasDistintas`. A secondary query must stay under 100 ms after the 1.08 period factor and under the weight of the lightest of the ten (share times time below about 0.27), or it becomes "Moderada" or enters the dashboard top ten: check both before adding one.
* The row of `TabelaTodasConsultas` opens the detail modal, so it does not use `ConsultaSql` (whose click expands the text in place): the SQL is a `TrechoSql` inside a `button`, the `tr` takes the click and moves the focus to that button first, which is what lets `Modal` give the focus back to the row when the modal closes. `DetalheConsulta` is a centered `Modal` with `tamanho="lg"` (the user asked on 12 October 2026 to replace the drawer on the right it first was, so `Modal` no longer has a `posicao` prop), and below 600px the bottom sheet every modal already is. Its SQL box reserves two lines (`min-height: 3em` on the `code`), which keeps the modal at one height, 645px at 760px of width for the 42 simulated queries, so the arrows of the footer stay under the pointer while stepping through the list and the whole modal fits 1280x720 without scrolling; measure both again after adding a block to it. "No período" goes from two columns to four from 600px of `detalhe-consulta`, where the longest value of the 30 days ("46 h 42 min") still fits. The marked terms come from `TrechoSql`'s `termos` prop: `destacarSql` takes the stretches from `intervalosMarcados`, which normalises the SQL one UTF-16 unit at a time so the positions still point into the original text. The mark color is `--busca-realce` in `temas.css`.
* Consultas SQL › Histórico (`PaginaHistoricoConsulta`, `REQUISITOS.md`, "Consultas SQL: Histórico") shows one query at a time and is one request, `GET /consultas/{id}/historico`, and one DTO, so its blocks cannot disagree: the query with the numbers of the period (the same `ConsultaDetalhadaDTO` the list returns), the two variations, the position by weight with the neighbour ids and the intervals. The intervals are the ones of the dashboard activity chart (`intervalosPorPeriodo` and `minutosPorIntervalo` in `regras/historicoConsulta.ts` repeat the table of the contract, and `historicoConsulta.test.ts` checks them against `janelasPeriodo`). The selection lives in the history state as `{ historico: { consulta, periodo } }` (`useSelecaoHistorico`, read through `lerSelecao`; `lerIdDaConsulta` only accepts letters, digits, `_`, `.`, `:` and `-`, because the id goes into the path of the route). `consulta` is `null` when the screen is opened from the menu: the page then asks `servicoConsultas.buscarMaisPesada` (the first of `GET /consultas`) and shows that one. The id is written to the state only when something changes (`mudarPeriodo` pins the loaded query, so a new period keeps the query on screen): writing it right after the first answer would change the dependency of the fetch and ask for the same history twice. The page keeps, beside each answer, the selection that produced it (`Carga.pedido`) and compares it by identity with the current one: any difference shows the skeleton at once (`trocando`), as on the other screens. A `404` is not an error state: `carregar` turns it into `NAO_ENCONTRADA`, which offers the heaviest query. A change of connection resets `consulta` to `null` from an effect in the page.
* `ConsultaEmAnalise` stays mounted outside `ConteudoAssincrono`, so the selector works while the blocks load. It shows the SQL of the loaded history when the requested query is the same (a change of period keeps the SQL and hides only the performance badge), the SQL of the suggestion that was just picked (`escolhida`) while its history loads, and skeleton lines otherwise (the arrows only know the id). Its SQL box reserves two lines, like the detail modal, so stepping through the queries does not move the blocks below. `SeletorConsulta` is a combobox on `CampoBusca`: the list opens on click, on typing and on the arrow keys, never on focus (the focus comes back to the field after a choice and after the clear button), each opening asks again (`abertura` is part of the key of the request) and the first request of an opening has no wait while the next ones wait 250 ms. Enter only chooses while the list on screen answers the text that is typed (`atualizadas`). Its panel takes `onPointerDown` with `preventDefault`, which keeps the focus in the field while an option is clicked or the list is scrolled. Esc closes the list and keeps the text; the second Esc is the native clear of `type="search"`.
* The two charts of Histórico (`GraficoHistorico`) repeat the small multiples of Resumo and import the CSS module of `GraficoEvolucao`, so a change of mark or of tooltip there reaches both. The "Pico" labels of both go through `posicionarRotulo` (`utilitarios/graficos.ts`): centred on the mark, or aligned with its edge when the centred text would cross the plot (a peak in the first interval ran over the y-axis ticks, seen on 18 October 2026). The time chart draws the average only: the maximum is in the tooltip and in the table, because it is often several times the average and flattened the line. Its unit is in the chart title, not in the ticks ("400 ms" wrapped inside the 52px axis). An interval without executions has `null` times, which leaves a gap in the area, and the chart then draws a dot on every point so an isolated interval does not disappear. In 7 days the x axis takes one tick per day (`iniciosDeDia`), or the day repeated on two ticks out of four. The skeleton of the screen reuses `RelatorioEmEspera`, `PainelEmEspera`, `GraficosEmEspera`, `EsqueletoDestaques` and `EsqueletoIndicadores`; `EsqueletoIntervalos` is in the file of `TabelaIntervalos`, with as many rows as the period has intervals. At 1320px of container every block of the skeleton is within 1px of the loaded one in the four periods (290, 290, 529 and 672, 1226, 1411 or 1503, with the sortable header): its lines are `1lh` high because the page line height is not 1.5, and the executions cell is `vertical-align: top` because as an inline box on the baseline it grew by a fraction of a pixel per row. Measure again after changing a block. `TabelaIntervalos` turns into cards below 480px of `intervalos-historico`, with the two time columns sized by their labels (`minmax(0, 1fr) auto auto`), which is what fits "Tempo máximo" at 320px.
* The timeline charts of Resumo (`GraficoEvolucao`), Comparação (`GraficoComparacao`) and Histórico (`GraficoHistorico`) have no floating tooltip since 22 October 2026 (it covered the neighbour bars and the peak labels): `useLeituraDoGrafico` takes `activeTooltipIndex` and `activeCoordinate.x` from `onMouseMove` of either chart, and `LeituraDoGrafico` writes the reading in the title row of each chart, hiding the title (`visibility`) and placing a chip at that x, clamped to the row by a layout effect. The Recharts `Tooltip` stays with `content={() => null}` only to draw the cursor band and line. The "Novo plano" label of the plan change goes on the side away from the volume peak (`ladoDoRotuloDaTroca`), because it ran over "Pico" when the peak followed the change. The performance bars of Resumo and Comparação have no tooltip either: `eventosDoFoco` (`DistribuicaoDesempenho.tsx`) links a segment and the table row of the same band, dimming the others (`.apagado`, `.linhaApagada`); a tap toggles it.
* The simulated history (`historicoConsulta.ts`) never changes the numbers of the list: `repartirExecucoes` splits the executions of the query among the intervals by largest remainder and accepts zero in an interval (`distribuirExecucoes` of the list forces at least one), the averages are normalised so that their weighted mean is the average of the query, and the highest maximum is set to the maximum of the query. Each fictitious query takes one of five behaviours by its place in the catalogue (`perfis`), all functions of the real time of the interval and not of its position in the window (follows the load, slower from 1h to 5h, slower on Mondays, a step up three days before today at 9h, steady), so the four periods of one query tell the same story. The heaviest query, the one the screen opens on, follows the load. The variations come from the same query in the previous window, from the values as the list carries them, as in the reports. A new `TipoDestaque` (`LENTIDAO`, the slowest interval) needs its icon in `DestaquesRelatorio`.
* "Ver histórico" sits at the right end of the footer of `DetalheConsulta` and navigates with `state: { historico: { consulta, periodo } }`, taking the period of the list that is on screen (`aplicados`), not the requested one. With it the modal is 645px tall at 760px of width for the 42 queries (it was 643px) and still fits 1280x720. Below 420px of viewport the word "Consulta" of the position is visually hidden so the footer fits 320px: arrows, "1 de 42" and the button.
* The ordering of `TabelaIntervalos` (asked on 12 October 2026) is done in the browser, unlike Consultas SQL › Todas: the whole series is already in the DTO. `ordenarIntervalos` (`regras/historicoConsulta.ts`) puts the intervals without executions last when sorting by a time, whatever the direction, and breaks ties by the start of the interval. The state (`ordem`) lives in `HistoricoConectado`, not in the table, because the table is unmounted while the skeleton is on screen; `EsqueletoIntervalos` takes it too, through the same `Moldura`, so the header and the sort buttons stay. It is plain React state on purpose: it survives a change of query and of period and is dropped on leaving the screen. The CSV ignores it and is always chronological. Below 480px the header is hidden and a "Ordenar por" select takes its place, with five fixed orders; an ascending order of a measure picked on a wide screen has no option there and the select reads "Outra ordem". The table is not paginated (30 rows at most; the user asked about paging on 14 October 2026 and took this instead): its header is sticky under the app header instead (`top` is `--altura-cabecalho` plus the safe area, so its top border lies under the header border), which needs `border-collapse: separate`, because collapsed borders stay behind when the cell sticks. A sort clicked while the header is stuck scrolls back to the top of the table (`ordenarDoCabecalho`), so the first rows of the new order show; the table has `overflow-anchor: none`, or the browser kept a moved row in place and the page jumped by its distance. Above 12 intervals (`INTERVALOS_RECOLHIDOS`) the table opens collapsed (asked on 14 October 2026): `recortarIntervalos` keeps the 12 most recent in the oldest-first order and the first 12 of any other order (`ladoDosOcultos`). The button (`AlternarIntervalos`) sits in the panel header beside "Exportar CSV" (the user asked on 14 October 2026; it was a row inside the table first), in `.acoesIntervalos`, whose children stretch when the two wrap. That needed `max-width: 100%` on `.acao` of `CabecalhoPainel`: with only `flex-shrink: 0` the action kept its one-line width and the page scrolled sideways at 390px. Below 360px of viewport the long label is visually hidden and a short one shows (`rotuloCurtoDoAlternador`, "Mostrar os 30 dias", "Mostrar só 12"), because "Mostrar os 16 intervalos anteriores" did not fit the 236px of the card at 320px. `expandida` lives in `HistoricoConectado` beside `ordem`, for the same reasons; `EsqueletoIntervalos` takes `total` and draws `quantidadeVisivel` rows, and the skeleton header draws `AlternarIntervalos` with `emEspera` (the real button with `visibility: hidden` under a skeleton bar, so the bar has its exact width), through the new `acao` prop of `PainelEmEspera`. The skeleton keeps the loaded height in the four periods, open or collapsed. The labels name the intervals in the word of the period (`artigo` and `plural` of `textosDoIntervalo`: "as 12 horas anteriores", "os outros 16 intervalos", "só as 12 primeiras").
* "Ver histórico" outside the query list (asked on 12 October 2026) goes through `useVerHistorico`, which navigates with `estadoDoHistorico`. `ConsultaSql` takes `aoVerHistorico` and draws the button between the toggle and the copy button, in a wrapper (`discreta`) that follows the same hover and focus rule as the copy button but has none of its confirmation phases; `TabelaConsultas` passes it on, so the Dashboard and Resumo get it. In the card layout that makes three buttons at the foot of the card, and at 320px they ran over the performance badge (seen on 13 October 2026), so below 420px of `consultas` the visible "Desempenho" label of that cell is dropped and the badge stands alone. `ConsultasComparadas` keeps `TrechoSql` alone in its narrow SQL column and puts the button in a last column of its own, always visible, which is absolute at the top right of the card below 860px and hidden in print; the column exists only when `aoVerHistorico` is given. The Dashboard opens the history in its own period. Resumo and Comparação show closed calendar periods and the history only has rolling windows, so they open the recent window of the same size (`periodoDoHistorico`) and say which one in the label of the button (`rotuloVerHistorico`): do not present that as the history of the period of the report.
* The filter bar of that screen has no visible labels (search icon and placeholder, a segmented control, a select that reads "Qualquer comando"): each control gets its name from a visually hidden label (`rotuloOculto` of `EstruturaCampo`, passed on by `CampoSelecao` and `CampoBusca`). Below 620px of `filtros-consultas` the segmented control gives way to a second select ("Qualquer desempenho"), because the four options do not fit at 320px; both are in the DOM and one is `display: none`. The table turns into cards below 860px of `lista-consultas`.
* "Exportar CSV" reads every page of the filtered list (`servicoConsultas.listarTodas`, 100 per page) and builds one file in the browser with `escreverCsv` and `comOrigem` of `exportacaoRelatorio`, so the formula guard and the "Origem dos dados" column are the same code as in Exportação. The button is `MenuExportarCsv` (the user asked on 12 October 2026 for the choice of number standard): it opens a `Flutuante` with the two standards, and the choice starts the download. Their labels and descriptions (`rotuloPadraoNumerico`, `descricaoPadraoNumerico`) live in `exportacaoRelatorio`, shared with `OpcoesExportacao`.
* The detail modal steps through the filtered list (asked on 12 October 2026): the arrows in its footer call `passoNaLista`, which answers with the neighbour on the page or with the next page and the end to land on. Crossing a page keeps the current query on screen, with both arrows `aria-disabled`, until the answer whose `pagina` is the awaited one arrives (`chegada` in `PaginaTodasConsultas`); do not compare filter objects there, because the router changes the location inside a transition and the old page would be taken for the new one. The arrows sit at the left of the footer on purpose: the notification card comes up at the bottom right and covered them when they were on the right of the drawer, and they kept the place in the centered modal. The row of the open query takes `aria-current`, which paints it and is what `TabelaTodasConsultas` scrolls into view, and `Modal` takes `focoAoFechar`, so the focus goes back to the row of the query that was open at the end, not to the one that opened the modal.
* Consultas SQL › Planos de execução (`PaginaPlanosExecucao`, `REQUISITOS.md`, "Consultas SQL: Planos de execução") is one request, `GET /consultas/{id}/plano?versao=`, and one DTO (`PlanosConsultaDTO` in `modelos/planos.ts`): the query with its numbers of the last 30 days, the position by weight with the neighbour ids, the plan versions and the chosen plan with its suggested indexes. The screen has no period: `PERIODO_DOS_PLANOS` (`ULTIMOS_30_DIAS`) feeds the selector, the position ("por peso em 30 dias", the `rotuloDaPosicao` of `ConsultaEmAnalise`) and its "Ver histórico". It reuses the shape of Histórico: the selection lives in the history state as `{ plano: { consulta, versao } }` (`useSelecaoPlano`, read through `lerSelecaoDoPlano`, which drops the version without a query), `consulta` is `null` from the menu and the page asks `buscarMaisPesada` in 30 days, `Carga.pedido` is compared by identity to show the skeleton at once, a `404` becomes `NAO_ENCONTRADA` and a change of connection resets the selection. A version that no longer exists answers with the current plan, and the page marks the version by `plano.id`.
* The plan DTO follows `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`: times and rows are per loop and `buffers` include the steps below, so the front multiplies (`tempoDoNoMs`, `linhasDevolvidas`) and subtracts (`tempoProprioMs`, `buffersProprios`); never show a raw per-loop value as a total. `tipo` is the PostgreSQL `Node Type` and `nomeDoNo` rebuilds the text-format name (`Hash Right Join`, `HashAggregate`, `Index Scan Backward`, `Update`); `planoEmTexto` and `planoEmJson` write the two copies back in the PostgreSQL format (tested line by line, recuo of 2 + 6 per level), so a field added to the DTO also goes into both writers. A step under a `Limit` that returned fewer rows than estimated is not an estimate error (`abaixoDeLimite` of `linhasDoPlano`, passed to `estimativaErrada`): the Sort under the `LIMIT 50` of the ranking query flagged 3.720 times before that rule.
* `ArvorePlano` is a real ARIA tree (`role="tree"`, flat `treeitem`s with `aria-level` and `aria-expanded`, roving `tabIndex`, selection follows focus; up and down, Home and End; right expands a collapsed step and otherwise goes to the first child, left collapses an open step and otherwise goes to the parent, as in the WAI-ARIA tree pattern). A step with children draws a chevron (`alternador`) in place of its dot, which collapses and expands the steps below it (asked on 20 October 2026); a collapsed step says how many steps it hides (`quantasEtapasAbaixo`). The collapsed set is state of the tree (`linhasVisiveis` of `regras/planoExecucao.ts` filters the rows), it starts empty for each plan, collapsing an ancestor of the selected step selects that ancestor, and selecting a hidden step from outside ("Ver X na árvore", the path of the detail) reopens its ancestors during render (`selecaoVista`). The rows a reopening reveals replay the entrance with `--ordem` counted from the step that opened. The guides from the first step down to the selected one are drawn in `--destaque` (`trilhaAte`: `passagens` are the guide columns crossed by the path, `chegada` the elbow into a step of the path, `desce` the line from a step down to its children), and `DetalheEtapa` opens with that path as buttons (`caminho`, `ancestraisDaEtapa`). Guides are 1px fills, not borders, so the arrival elbow can be half accent and half guide with a gradient; their color is `--guia-arvore` (new in `temas.css`), because `--borda-forte` was nearly invisible on the dark surface. The read-only list of the comparison has neither chevrons nor the path. The guides are drawn from `guias` of `linhasDoPlano` (`VAZIA`, `LINHA`, `RAMO`, `ULTIMO`) plus a dot per step and, on a step with children, a line from its dot to the bottom of the row (`comFilhos`), which is what joins a parent to its children; the text starts one `--recuo` after the guides for that line to pass. Below 620px of `arvore-plano` the header goes and the time and the rows stack under the name: side by side they overlapped at 320px (seen on 14 October 2026). The tree is keyed by `plano.id` through `ConteudoDoPlano`, which also starts on the slowest step.
* The layout of Planos de execução is a grid with areas: the tree and, below it, "Índices sugeridos" and "Mudanças de plano" on the left, the step detail on the right spanning both rows. With the extras in a row of their own, a one-step plan left a hole as tall as the detail beside the tree. The detail is sticky inside its cell (`.fixo`) with a `max-height` of the viewport and its own scroll; below 900px of `planos-execucao` everything stacks and a click on a step scrolls to the detail when it is below the fold. "Ver X na árvore" in the diagnosis and the suggestions selects the step, focuses it and scrolls it to the centre; the link shows only on the first sentence of each step and not at all on a one-step plan, where it repeated the same target three times.
* The simulated plans (`dados/simulacao/planosExecucao.ts`) are models with the exclusive share of time of each step (`parte`) and its own blocks, turned into a DTO by `materializar` with the execution time of the version (its average times a 0.93 to 1.07 noise). `q-pedidos-cliente` has two versions split at its plan change (`trocasDePlano.ts`, at `marcoDoDegrau`), the step the Histórico shows, and their executions and weighted average come from the 30-day history points, so the two screens tell the same story; `planosExecucao.test.ts` enforces it, plus that every query but COMMIT, ANALYZE and REFRESH has a plan, that the root rows of a SELECT match `linhasPorExecucao`, that no child takes more time than its parent and that each suggestion points at a step of its table with a filter. `registradoEm` is stable within a 10-minute bucket.
* The comparison of two plans is a third field of the selection, `comparacao` (`lerSelecaoDoPlano` drops it when it equals `versao`): `carregar` asks `GET /consultas/{id}/plano` for both versions in parallel and `CorpoPlanos` shows `ComparacaoPlanos` only when both answers have a plan and their `plano.id` differ (a version that expired comes back as the current one, which would compare a plan with itself). The left side is always `versao`; "Inverter" swaps the two ids, "Fechar comparação" keeps the left one and any card of "Mudanças de plano" opens that version alone. `ArvorePlano` without `aoSelecionar` is a read-only list (`role="list"`, items with `aria-level`, no focus, no hover) and takes `alteradas`, the steps of the tables read another way (`etapasAlteradas`; the Bitmap Heap Scan takes the index of its Bitmap Index Scan, so both get the "Mudou" badge). The badge is as tall as the name line (`.cabecaDaEtapa .seloDaEtapa`), or the dot and the guide tick would leave the name. A difference of 10 times or more is written as `139.536×` (`razao`, `RAZAO_EM_VEZES`), because the percentage reached `+13.953.471,4%`. The table turns into cards below 520px of `comparacao-planos` and the two trees stack below 860px of `lados-dos-planos`.
* The plan change of the history (`trocasDePlano` in `HistoricoConsultaDTO`) comes from `dados/simulacao/trocasDePlano.ts`, the same module that splits the plan versions, which also owns `marcoDoDegrau` now: the history step, the plan change and the versions are one instant, and `planosExecucao.test.ts` checks that the history of 7 days carries the change and the one of 24 hours does not. `intervalosComTroca` (`regras/historicoConsulta.ts`) turns each change into the start of the interval that holds it; `GraficoHistorico` draws a dashed `ReferenceLine` there on both charts (gray, `--texto-secundario`, so it is not read as a series of `--grafico-1`; the label "Novo plano" only on the top one), the tooltip of that interval says so and `TabelaIntervalos` adds the "Novo plano" badge. With a change in the period the description of "Evolução no período" grows by one sentence and the header gets "Comparar os planos", so that panel is taller than its skeleton for that query: the skeleton cannot know about the change before the answer.
* "Ver plano" goes through `useVerPlano`. `ConsultaSql` takes `aoVerPlano` (a fourth `discreta` button, `ListTree`, after the history one) and `TabelaConsultas` passes it on; at 320px the worst card keeps 13px between the "Moderada" badge and the four buttons. `ConsultasComparadas` puts both buttons in its last column (`atalhos`, sized for two). The footer of `DetalheConsulta` has "Ver plano" and "Ver histórico" (shortest first) and keeps 645px at 760px of width; below 520px of viewport both labels are visually hidden. The `identificacao` row of `ConsultaEmAnalise` wraps, because the extra action (`acao`, "Ver plano" in Histórico and "Ver histórico" in Planos) overflowed at 390px.
